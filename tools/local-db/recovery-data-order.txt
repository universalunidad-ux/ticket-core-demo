# ADVERTENCIA — DEPENDENCIA CIRCULAR (hallazgo de esta unidad, no cubierto
# explicitamente por 01-08 previos): tickets.solicitud_soporte_id references
# solicitudes_soporte(id) [creado en el CREATE TABLE, linea 10 de
# 20260715023821_tickets_and_events.sql] Y solicitudes_soporte.ticket_id
# references tickets(id) [agregado por ALTER TABLE ... ADD CONSTRAINT
# solicitudes_soporte_ticket_id_fkey, lineas 70-72 del mismo archivo].
# NINGUNA de las dos FKs es DEFERRABLE (no se encontro la palabra clave
# `deferrable` en su definicion). Ambas son nullable (`on delete set null`).
#
# Implicacion para el restore: con constraints NO deferrable e INMEDIATOS,
# un `pg_restore --data-only --single-transaction` que cargue ambas tablas
# puede fallar por referencia circular si `DISABLE TRIGGER USER` (03/E) no
# desactiva los triggers internos de integridad referencial (RI) — `USER`
# solo desactiva triggers definidos por el usuario, no los RI internos de FK.
#
# MITIGACION PROPUESTA (a validar en vivo, PLANIFICADO):
#   a) Cargar ambas tablas con su columna circular (ticket.solicitud_soporte_id
#      y solicitudes_soporte.ticket_id) en NULL vía --column-inserts filtrado,
#      luego UPDATE de backfill con los valores reales tomados del dump; o
#   b) `ALTER TABLE ... DISABLE TRIGGER ALL` (no solo USER) exclusivamente
#      sobre estas 2 tablas, como owner, durante la carga, y reactivar tras
#      commit; o
#   c) Confirmar en runtime real si Postgres administrado por Supabase permite
#      `DISABLE TRIGGER ALL` sin superuser (a partir de PG 9.x el propietario
#      de la tabla puede hacerlo; pendiente de confirmar en el entorno objetivo).
